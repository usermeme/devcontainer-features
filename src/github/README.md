
# GitHub CLI & Restricted Token Auth (github)

Installs GitHub CLI (gh) if not present, forwards the host's DEVCONTAINER_GITHUB_TOKEN into GH_TOKEN and GITHUB_TOKEN inside the container, and configures Git to authenticate over HTTPS using that token.

## Example Usage

```json
"features": {
    "ghcr.io/usermeme/devcontainer-features/github:1": {}
}
```

## Options

| Options Id | Description | Type | Default Value |
|-----|-----|-----|-----|
| version | GitHub CLI (gh) version to install when gh is not already present (e.g. 'latest' or '2.67.0') | string | latest |
| gitProtocol | When 'https', rewrites git@github.com: and ssh://git@github.com/ remotes to https://github.com/ in system Git config so git push/pull uses the restricted token instead of forwarded host SSH keys | string | https |

## Host setup

Create a fine-grained Personal Access Token on GitHub scoped only to the repositories and permissions you want the container to have (for example, **Contents: Read and write** and **Pull requests: Read and write** on a single repository), and export it in your host `~/.zshenv`:

```sh
export DEVCONTAINER_GITHUB_TOKEN="github_pat_..."
```

Keeping it under `DEVCONTAINER_GITHUB_TOKEN` on the host leaves your host's `GH_TOKEN` / `GITHUB_TOKEN` and `gh auth` login untouched.

`${localEnv:...}` is resolved by the process that launches the container (VS Code, JetBrains, `devcontainer` CLI), so use `~/.zshenv` rather than `~/.zshrc` on macOS/Linux: an app started from the Dock/Finder only inherits the login environment, and VS Code must be restarted after the variable changes (`launchctl setenv DEVCONTAINER_GITHUB_TOKEN github_pat_...` is the macOS GUI alternative). Check what the container will actually receive, from the shell (or app) that starts it:

```sh
devcontainer read-configuration --workspace-folder . | tail -n 1 | jq '.configuration.remoteEnv'
```

If the variable is unset, the feature still defines `GH_TOKEN` / `GITHUB_TOKEN`, as empty strings (`{"DEVCONTAINER_GITHUB_TOKEN":"","GH_TOKEN":"","GITHUB_TOKEN":""}`). In Codespaces that also shadows the `GITHUB_TOKEN` Codespaces injects for the signed-in user, so `gh` and `git push` fail with no obvious cause. Always provide the token before rebuilding, or leave this feature out of configurations that have none.

## Organization setup

A personal access token is always owned by a user; it cannot be created "by" an organization. What an organization controls is **which of its repositories a fine-grained token may reach** and whether it approves the request. So there are two ways to wire a team up.

### 1. Each developer creates their own org-scoped fine-grained token (recommended)

One-time, by an organization owner:

1. **Organization Settings → Personal access tokens → Settings → Fine-grained tokens** and allow access via fine-grained tokens (instead of restricting them).
2. Same page: set **maximum lifetimes**, and pick **Require administrator approval** (the default) or **Do not require administrator approval**.

Then each member:

3. **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**.
4. **Resource owner**: the organization. This option only appears when the organization allows fine-grained tokens and the user has access to it.
5. **Repository access**: only the repositories the container needs (not "All repositories").
6. **Permissions**: `Contents: Read and write`, `Pull requests: Read and write` (`Metadata: Read` is implied). Add `Workflows: Read and write` only if the container must push workflow files, because `git push` is rejected without it.
7. **Expiration**: within the organization's maximum lifetime.
8. If approval is required, the token stays pending until an owner approves it under **Organization Settings → Personal access tokens → Pending requests**. Tokens generated by an organization owner skip approval.
9. Export the value on the host as `DEVCONTAINER_GITHUB_TOKEN` (see [Host setup](#host-setup)).

Never hand one person's token to the whole team: a PAT dies with that person's membership and its permissions are the creator's, so offboarding and auditing break.

### 2. One organization secret for GitHub Codespaces

For Codespaces, `${localEnv:DEVCONTAINER_GITHUB_TOKEN}` resolves against the codespace's own environment (for a cloud service "the host is in the cloud"), and Codespaces secrets arrive there as environment variables. So a single secret named `DEVCONTAINER_GITHUB_TOKEN` feeds this feature with no per-developer export:

**Organization Settings → Secrets and variables → Codespaces → New secret**, name `DEVCONTAINER_GITHUB_TOKEN`, the token value, and a **Repository access** policy.

Requires an organization owner; organization-level Codespaces secrets are available to public repositories on any plan but to private repositories only on GitHub Team or GitHub Enterprise. The same secret name can also be stored under **Secrets and variables → Actions** for CI (used as `${{ secrets.DEVCONTAINER_GITHUB_TOKEN }}`) and in each user's personal Codespaces secrets (which take precedence over the organization value).

### Tokens for automation

For CI, prebuilds, or anything else that outlives an individual, do not mint a PAT from a person's account: use a GitHub App installation token (short-lived, revocable, org-owned) or a dedicated machine-user account. Share the credential *source*, not the credential.

## What it configures in the container

- **Environment (`remoteEnv`)**: Forwards `${localEnv:DEVCONTAINER_GITHUB_TOKEN}` into `GH_TOKEN`, `GITHUB_TOKEN`, and `DEVCONTAINER_GITHUB_TOKEN` inside the container. Because it uses `remoteEnv` rather than `containerEnv`, the token is not baked into the image or container config (`docker inspect`).
- **GitHub CLI (`gh`)**: Installs the official `gh` release binary (verified against `gh_<version>_checksums.txt`) if `gh` is not already installed on the image. With `GH_TOKEN` set, `gh pr create`, `gh pr view`, `gh api`, etc. authenticate immediately without `gh auth login` or writing tokens to `~/.config/gh/hosts.yml`.
- **Git credential helper**: Configures `/etc/gitconfig` (`--system`, so a stowed `~/.gitconfig` from the `dotfiles` feature is never modified on the host) to authenticate `https://github.com` and `https://gist.github.com` via `gh auth git-credential`.
- **SSH-to-HTTPS remote rewrite (`gitProtocol: "https"`, default)**: Adds `url."https://github.com/".insteadOf` for `git@github.com:` and `ssh://git@github.com/` in `/etc/gitconfig`. Even if the repository on the host was cloned over SSH and VS Code forwards `SSH_AUTH_SOCK`, `git push` and `git fetch` inside the container go over HTTPS and are bound to the restricted `DEVCONTAINER_GITHUB_TOKEN` permissions instead of your unrestricted host SSH key. Set `"gitProtocol": "ssh"` to disable this rewrite.
